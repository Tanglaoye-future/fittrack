## 1. 产品定位

### 一句话

> **FitFlow Pro 是为职业健美运动员打造的"备赛操作系统"——把训练、饮食、消费、备赛周期、教练协同的全部数据，收敛在一个低认知负荷的入口中。**

### 与 v1 的根本差异

| 维度 | v1 (FitFlow 通用版) | **v2 (FitFlow Pro 专业版)** |
|---|---|---|
| 目标用户 | 所有健身爱好者 | 职业 / 高级业余健美运动员 + 健美教练 |
| 核心场景 | 每天打开 1–3 次看看数据 | 每天打卡 6–10 次，训练中边练边记 |
| 训练颗粒度 | 一条记录 = 一个动作 | 训练日 → 动作 → 单组（含 RIR / RPE / Tempo） |
| 饮食颗粒度 | 自填食物名 + 估算热量 | 食材称重（g）+ 配方 + macros 自动反算 |
| 消费颗粒度 | 6 个泛分类 | 12 个健美专属分类 + 月度预算 + ROI |
| 体测内容 | 围度 + 体脂 | + 4 角度照片 + 主观条件评分 + 晨重曲线 |
| 备赛能力 | 无 | 5 阶段周期管理 + 自动 macros / cardio 推算 |
| 教练能力 | 无 | 多对多协同 + 每周 check-in + 调整下发 |
| 客户端 | Web | **Next.js PWA（离线优先 + 可装桌面）** |
| 商业模式 | 免费 + 高级功能付费 | 运动员订阅 + 教练 SaaS 多席位 |

### 产品边界（明确不做的事）

- ❌ 不做社区 / 动态 / 关注（避免分散注意力，与"降低认知负荷"违背）
- ❌ 不做"今日推荐健身餐"等内容平台功能
- ❌ 不做付费课程销售
- ❌ 不做硬件（智能秤、心率带）—— 通过 API 集成第三方
- ❌ 不在公网商店做 PED 模块入口（合规风险，仅"个人健康日志"形态，对运动员-教练私域可见，详见 §5.5）

## 2. 目标用户画像（3 类核心用户）

### 用户 A：备赛中的职业健美运动员（核心）

- 年龄 22–38，男 70% / 女 30%
- 一年 1–2 次正式比赛，备赛期 16–20 周
- 备赛期每天：5–6 餐 + 1–2 次训练 + 1 次有氧 + 10+ 次补剂打卡
- **痛点**：手机里同时开着 MyFitnessPal、Hevy、Notion、备忘录、Excel、微信教练对话——切来切去
- **核心诉求**：**少做一次决策、少切一次 App、少做一次心算**

### 用户 B：健美教练（高 ARPU 用户）

- 年龄 28–45，自由职业 / 工作室
- 同时带 8–25 名学员
- 每周日花 4–8 小时看每个学员的 check-in 写反馈
- **痛点**：学员发来的数据格式五花八门（截图、文字、Excel），整合统计极费时
- **核心诉求**：**一个看板看完所有学员，标准化 check-in，调整一键下发**

### 用户 C：高级业余选手（潜在付费意愿）

- 备赛和工作并行，时间更碎片化
- 没有专职教练，需要"产品当半个教练"——主要靠备赛模板
- **核心诉求**：开箱即用的 12 周备赛模板 + 自动 macros 推算

## 3. 三个核心闭环（必须先跑通的产品骨架）

> 这 3 个 Loop 跑通 = 产品成立；任何一个跑不通 = 加再多功能都是噪音。

### Loop A — 训练日 Daily Loop（频次最高，认知负荷最敏感）

```
打开 App
  → 主页正中：今日训练卡片"胸+三头（来自模板）"
  → 点 [开始训练]
  → 第一个动作（卧推）的第一组数据已经预填"上次：100kg × 8 reps, RIR 1"
  → 用户只需 weight ±2.5kg / reps ±1 → 点 [完成]
  → 自动启动 90s 组间休息倒计时（与该模板配置同步）
  → 计时归零自动跳到下一组，并震动提醒
  → 全部完成 → 自动生成 Session Summary（总组数、总吨位、平均 RPE）
  → 询问 1 个主观问题"今日整体感觉？1–10"
```

**目标**：单组录入 ≤ 3 次点击、≤ 5 秒；整次训练用户额外操作 ≤ 30 次。

### Loop B — 饮食日 Daily Loop

```
早晨 7:00
  → 通知推送"今日 5 餐计划已就绪（基于备赛 Week 8 macros：3200kcal / 250P / 350C / 80F）"
  → 主页显示 4 个进度环：kcal / P / C / F
  → 第 1 餐到点
  → 通知"早餐：燕麦碗 + 鸡胸（450kcal）"
  → 点 [吃完了] → macros 自动累加
  → 临时换菜：从食材库搜"红薯" → 输入 200g → 自动反算 macros
  → 训练前 30 分钟自动推 "记得 pre-workout（咖啡因 200mg + β-丙氨酸）"
  → 睡前主页提示"今日蛋白还差 22g，建议补一勺乳清"
```

**目标**：常规一餐打卡 1 次点击；非常规一餐（自由餐）≤ 4 次点击。

### Loop C — 每周教练 Check-in（核心商业价值锚点）

```
周日 20:00
  → 通知"本周 check-in 时间到，系统已为你预填数据"
  → 表单已自动填好：
      - 过去 7 天平均晨重：82.4kg（↓0.3kg）
      - 平均 kcal 摄入：3180（目标 3200，达成 99%）
      - 平均步数：12,400
      - 训练完成率：6/6
  → 用户只需补 3 项：
      - 4 张照片（前 / 后 / 左侧 / 右侧）
      - 主观条件评分 1–10
      - 自由文字（150 字以内可选）
  → 提交 → 教练收到通知
  → 教练 24h 内回复，并可直接在系统中调整下周 macros / cardio
  → 系统自动按新 macros 重排下周餐食模板
```

**目标**：运动员填表 ≤ 5 分钟；教练评注一个学员 ≤ 8 分钟。

## 5. 关键设计决策（理由记录）

### 5.1 训练模型为什么必须做成三层（Session → Exercise → Set）

职业健美的训练数据是分析的核心源。教练看的是"过去 8 周卧推第 3 组的力量曲线"，这需要 SetEntry 级别的明细。把每组单独存为一行还有以下好处：

- 支持 Drop set / Rest-pause / Myo-rep 等高级训练法（用 `set_type` 区分）
- 支持热身组与正式组分别统计
- 支持 RIR / RPE 趋势分析（看是否在 over-reaching）
- 支持 PR 自动检测（每次新 set 写入时实时对比历史最大值）

### 5.2 营养模型为什么必须有 Foods 全局库

如果让用户每餐手填"鸡胸 200g, 30g 蛋白"，会出现两个灾难：

1. 数据不可比（用户写法千变万化）
2. 用户每次都要查 macros，违反"零数学"准则

所以 **Foods 是全局共享的（含官方+用户贡献），Meals 只引用 food_id + grams，所有 macros 由系统反算并缓存**。

### 5.3 备赛周期为什么独立成域

备赛阶段（PREP）和淡季（OFFSEASON）下的所有规则都不同：

- macros 目标不同（PREP 是 cut，OFFSEASON 是 lean bulk）
- 训练量不同（PREP 加有氧，OFFSEASON 加力量）
- 体测频率不同（PREP 每天晨重，OFFSEASON 每周）
- 提醒策略不同（PREP 严格执行，OFFSEASON 放宽）

把 PrepCycle 抽象成"全局状态"，所有其他模块订阅它，避免每个模块各自判断 if (in_prep)。

### 5.4 教练模型为什么是多对多

- 一个运动员可能同时有：力量教练 + 营养教练 + Posing 教练
- 一个教练可能带 8–25 名学员
- 必须支持"教练只看到自己学员的特定模块"（例：营养教练看不到训练数据）

`CoachAthleteLink` 表设计为 `(coach_id, athlete_id) + scope_* booleans`，**模块级**权限（修订 R2，评审 P1-11；详见 SCHEMA §10.2）。模块包括：训练 / 营养 / 体测基础 / 体测照片 / 消费 / 受控物质。

**教练能改什么，不能改什么**（修订 R2 评审 P1-21）：

| 教练可以做 | 教练不可以做 |
|---|---|
| 通过 `/coach/.../adjustments` 修改下周 `MacroTarget` | 直接改运动员的过去任何记录 |
| 通过 `/coach/.../training-adjustments` 覆盖下周 `TemplateExercise` 目标 | 改运动员的当前进行中 `WorkoutSession` |
| 在 check-in / session / meal / photo 上评论（CoachComment） | 删除运动员的数据 |
| 申请 ControlledViewToken 查看受控物质（脱敏视图） | 主动给运动员开启受控模块 / 设 PIN |
| 给运动员签发训练 / 餐单模板 | 修改运动员的订阅档 / 隐私设置 |

> 注：Athlete Pro 档同时**只允许**关联 1 名教练；如需切换需先终止旧合作。Coach 档无此限制（教练自己作为运动员账户时也受此限制）。详见 SCHEMA §10.2 partial unique。

### 5.5 PED 模块的合规边界（用户已确认完整做）

PED（Performance Enhancing Drugs，包括类固醇、HGH、胰岛素等）在职业健美圈是公开的事实，但在大众应用商店是高风险类目。本产品的处理方案：

| 维度 | 策略 |
|---|---|
| **入口可见性** | 仅在"专业模式"开关打开后才可见；默认关闭 |
| **数据可见性** | 仅本人 + 已授权教练；不进任何排行榜 / 公开页 / 分享 |
| **数据传输** | 端到端加密标签，导出时单独密码保护 |
| **法律定位** | 定位为"个人健康日志"（类似糖尿病人的胰岛素日志），不提供购买、不提供医嘱 |
| **免责声明** | 启用模块前需阅读并勾选"我已理解本模块仅供个人记录，本产品不提供任何医疗建议、不参与任何物质交易" |
| **应用商店** | 在 App Store / Play Store 提交时该模块默认关闭并不出现在截图中 |
| **导出** | PED 数据导出时使用独立密码，与主导出分开 |

**实现位置**：作为 `Supplements` 模块的扩展字段 `is_controlled` + 独立的 `ControlledCycle` 子表，详见 SCHEMA。

### 5.6 客户端为什么选 PWA

用户决策已定：Next.js PWA。理由：

- 一套代码同时跑 Web / iOS / Android（装到桌面后等效于 App）
- 离线优先 + 后台同步（IndexedDB + Service Worker）— 健身房经常没信号
- 无需 App Store 审核延迟，迭代速度快
- 安装成本低，分享链接即可
- 后续若验证商业模式后再做 React Native 原生 App（v3 计划）

## 6. 商业模式

### 6.1 三档订阅

## 7. 成功指标（北极星 + 关键里程碑）

### 北极星

> **"备赛运动员每周完整记录 ≥ 6 天的比例"**（衡量产品能否真正降低认知负荷到运动员愿意天天打开）

**"完整记录的一天"定义（修订 R2 评审 P1-28）** —— 由 `DailySummary.is_complete: Boolean` 计算，详见 SCHEMA §11：

```
当日同时满足下列 4 条 → is_complete = true：
  1. meals_count ≥ 当日 ScheduledMeal 总数 × 80%  且  ≥ 4 餐
  2. workout_minutes > 0  或  当日 PhaseConfig 摊到当日的有氧任务已记录
  3. morning_weight_kg IS NOT NULL
  4. supplement_logs_count ≥ 当日 SupplementSchedule 总条目 × 80%

由 DailySummaryRebuildJob 在每日 00:30（用户本地时区）回算。
"备赛运动员"= subscription.tier=ATHLETE_PRO 且 当前有 active PrepCycle。
"每周 ≥ 6 天" = 滚动 7 日窗口内 is_complete=true 的天数 ≥ 6。
```

### 12 周内的关键指标目标

| 指标 | 目标 |
|---|---|
| 单组训练录入时间中位数 | ≤ 5 秒 |
| 单餐打卡时间中位数 | ≤ 8 秒 |
| 周 Check-in 表单填写时间 | ≤ 5 分钟 |
| 教练每名学员评注时间 | ≤ 8 分钟 |
| 离线状态下数据写入成功率 | 100% |
| 离线数据同步成功率 | ≥ 99.9% |
| PWA Lighthouse PWA 分数 | ≥ 95 |
| 种子用户连续 4 周完整记录留存率 | ≥ 60% |

## 8. 风险与对策

| 风险 | 级别 | 对策 |
|---|---|---|
| PED 模块导致应用商店下架 | 高 | §5.5 的分发策略；商店版默认关闭，单独 sideload 版面向高级用户 |
| 训练录入 UX 不够快，运动员弃用 | 高 | W3–W4 必须做 5 人真实健身房测试，单组 ≤ 5 秒不达标就重做 |
| 食材库初始内容不足 | 中 | 上线前预导入中国营养学会食材库 1000+ 条目 |
| 教练端 ARPU 不足以养系统 | 中 | 早期不做教练端商业化，先做体验，验证 NPS ≥ 50 再加价 |
| 离线同步冲突（多端编辑同一记录） | 中 | 所有写操作携带 `client_op_id`（UUID）+ `client_ts`，服务端用 LWW + 字段级合并 |
| 数据迁移：现有 v1 用户数据 | 低 | v1 没有真实用户（项目还在 MVP 阶段），无需迁移 |
